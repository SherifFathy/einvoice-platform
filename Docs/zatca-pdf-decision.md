# ZATCA PDF Generation: Architecture Decision Record

**Date**: 2026-04-19
**Status**: Decision made
**Scope**: Wave 3 (post-MVP) — not implemented in this wave

## Context

ZATCA requires that printed tax invoices include a scannable QR code containing TLV-encoded data (Tags 1-8). B2B standard tax invoices may optionally be rendered as PDFs for customer delivery, while B2C simplified invoices should include the QR as part of the printed receipt.

The QR code image is already generated by `ZatcaQrService` (ZXing PNG output) and stored as a `QR_CODE` artifact during submission. The question is how and when to generate the final PDF.

## Decision

**Defer PDF generation to Wave 3.** The QR code artifact is already available. PDF rendering is a presentation concern that does not affect ZATCA compliance (ZATCA receives the XML, not the PDF).

### Recommended approach for Wave 3

Use **Apache FOP** (XSL-FO) or **iText/OpenPDF** to render the signed XML + QR code into a printable PDF:

1. **Input**: Signed XML (from `SIGNED_XML` artifact) + QR code PNG (from `QR_CODE` artifact)
2. **Template**: XSL-FO stylesheet that maps UBL 2.1 elements to a printable layout
3. **Output**: PDF stored as `ETA_PDF`-equivalent artifact type (add `ZATCA_PDF` to `ArtifactType` enum)

### Why Apache FOP or OpenPDF

| Option | Pros | Cons |
|--------|------|------|
| **Apache FOP (XSL-FO)** | Template-driven, easy to update layout without Java changes; standard for invoice PDFs | XML-based templates can be verbose |
| **OpenPDF / iText** | Programmatic control; widely used; HTML-to-PDF via Flying Saucer | Harder to maintain layout changes; iText AGPL concerns |
| **Jasper Reports** | Visual designer; mature | Heavy dependency; over-engineered for simple invoices |
| **Browser-based (Angular → PDF)** | No server dependency; matches screen layout | Cannot guarantee pixel-perfect ZATCA layout; QR code must be embedded client-side |

### Storage

PDF artifacts follow the same immutable pattern as all other artifacts:
- Stored in `invoice_artifacts` table with type `ZATCA_PDF` (new enum value needed in Wave 3)
- SHA-256 content hash for integrity verification
- Insert-only, no updates

### API

```
GET /api/invoices/{id}/zatca-pdf → downloads the PDF (generates on first request, caches thereafter)
```

Same pattern as `GET /api/invoices/{id}/eta-pdf` for ETA invoices.

## Consequences

- Wave 2 ships without ZATCA PDF rendering capability
- QR code data is available as a base64 string and PNG artifact for future use
- No additional dependencies needed in this wave
- Wave 3 will add Apache FOP or OpenPDF dependency and a `ZATCA_PDF` artifact type
