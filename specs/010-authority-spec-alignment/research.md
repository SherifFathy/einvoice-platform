# Research — Authority Spec Alignment (Feature 010)

## Overview

Per the locked Assumptions in [`spec.md`](./spec.md), three design-input documents in `/Docs/` are the authoritative research output for this feature. plan.md MUST reference them rather than restate their content. This file consolidates the pointers, names the additional plan-level decisions made on top of them, and lists alternatives considered and rejected.

All eight decisions below are locked. No NEEDS CLARIFICATION remains.

---

## Decision 1 — UBL XML field mapping (ZATCA Standard + Simplified)

**Decision**: Use the field-mapping reference card in [`Docs/zatca-spec-alignment.md`](../../Docs/zatca-spec-alignment.md) §12 as the authoritative ZATCA UBL XPath ↔ DB column mapping. The Wave 8 serialiser is updated to consume the new sub-tables (`zatca_*_tax_subtotals`, `zatca_*_allowances`, `zatca_*_line_allowances`) and the promoted party columns.

**Rationale**: The doc was reviewed against `Data/Schemas/xsds/UBL2.1/xsd/maindoc/UBL-Invoice-2.1.xsd` and `Data/Rules/schematrons/20210819_ZATCA_E-invoice_Validation_Rules.xsl` (Fatoora SDK v2.0.3). Eighteen decisions locked 2026-05-25 and bound to spec.md Clarifications.

**Alternatives considered**:
- Re-derive mapping from scratch using only UBL XSDs — rejected as needless duplication of completed work.
- Generate the mapping from JAXB binding — rejected because UBL XSD is too permissive and schematron post-validation would still be required.

## Decision 3 — Migration sequencing and PR cadence

**Decision**:
1. V58 — header additions + party promotion + ETA receipt restructure
2. V59 — ZATCA sub-tables (`tax_subtotals`, `allowances`)
3. V60 — line-block + line-allowance child + ETA receipt line restructure
4. V61 — signature artifacts + best-effort `zatca_configs` backfill

Four PRs, strict merge order, each carrying its migration plus the paired entity/serialiser updates.

**Rationale**: Each migration is non-breaking for the prior schema (additive first, destructive after backfill — FR-003). Splitting by migration gives per-PR rollback granularity and reviewable scope (Clarifications 2026-05-26).

**Alternatives considered**:
- One PR with all four migrations — rejected due to review burden and inability to stage-verify each step independently.
- V58 + V59 bundled vs V60 + V61 bundled — rejected; V60's `unit_price → item_net_price` rename has wide enough blast radius to deserve its own PR.

## Decision 4 — Manual verification scripting

**Decision**: Two standalone PowerShell scripts under `scripts/verify/`:
1. `fatoora-validate.ps1` — drives `fatoora -invoice <xml> -validate` over a developer-provided sample XML serialised from a Wave-8 DB row. Outputs zero `BR-KSA-*` errors required for SC-001/SC-002.
2. `eta-receipt-submit.ps1` — POSTs an ETA Receipt v1.2 sample JSON to `api.preproduction.invoicing.eta.gov.eg` and writes the response to a sibling `.log` file. Captures structural acceptance per SC-003.

Invoked manually by a developer pre-release. No CI gate, no scheduling. Findings land in the sibling `.log` next to the invocation directory.

**Rationale**: Locked 2026-05-26. Avoids CI infrastructure investment for a workload that runs at most a handful of times per release.

**Alternatives considered**:
- CI gate on every PR — rejected (brittle, slow, secret-management overhead).
- Nightly scheduled job — rejected (still requires a scheduler and recurring-run state).
- Maven integration-test profile — rejected (still pulls Fatoora CLI into the build, slows local `mvn verify`).

## Decision 5 — Smart-application / dumb-database stance

**Decision**: V58–V61 are limited to `ALTER TABLE ADD/DROP/RENAME COLUMN` (with type + `DEFAULT`), `CREATE TABLE` with `PRIMARY KEY` only, `CREATE INDEX`, `UPDATE` backfills, and `RAISE NOTICE`. Every `CHECK`, `UNIQUE`, `FOREIGN KEY`, `NOT NULL` is deferred to a downstream "constraint layer" spec via `deferred-validation.md`. The `zatca_uuid VARCHAR(255) → UUID` type change is abandoned.

**Rationale**: Locked 2026-05-26. Constitution Principle XIII (Validation Layering) already designates the backend as the source of truth for all final validation; deferring DB constraints is consistent. Pre-production data volume is small, all current write paths go through JPA (which respects Bean Validation), and the FR-021 audit logs deferred-rule violations during backfill.

**Alternatives considered**:
- Strict DB enforcement (`CHECK` + `UNIQUE` + `FK` + `NOT NULL`) — rejected per user direction; trade-off is stronger immediate safety vs. higher migration complexity and harder constraint evolution.
- Hybrid (keep `FK` + `UNIQUE` on new tables, defer `CHECK` only) — rejected at iteration 3 of clarification.

## Decision 6 — Reporting and audit channel

**Decision**: Single channel per tool, plain log only. V58–V61 emit `RAISE NOTICE` for findings (duplicates, mismatches, unresolved config linkages, deferred-rule violations) which lands in the Flyway `mvn flyway:migrate` output and the schema-history audit. FR-019/FR-020 manual scripts write a sibling `.log` file. No `migration_findings` table, no notifications, no automated gate. Developer review of the log is the promotion gate.

**Rationale**: Locked 2026-05-26. Matches the manual-only verification stance.

**Alternatives considered**:
- Dedicated `migration_findings` table — rejected as over-engineering.
- Slack / email notifications — rejected as out-of-scope infra.

---

## Decision 7 — Pre-V46 signature backfill

**Decision**: V61 uses a two-pass best-effort backfill for `zatca_config_id`:
1. Match the active `zatca_configs(company_id, authority_environment_id)` row.
2. Fall back to the most-recent historic/inactive row.
3. Leave NULL + `RAISE NOTICE` if both miss.

SC-008 is relaxed to apply only to documents with recoverable signature artifacts in `zatca_response_data`. The column is explicitly nullable in the schema; V61 carries an inline comment documenting why.

**Rationale**: Locked 2026-05-26. Wave 7/8 dev/staging produced rows that legitimately predate V46; aborting V61 would block migration over legacy test data.

**Alternatives considered**:
- Abort V61 on unresolvable rows — rejected; blocks migration over legacy test data.
- Hard-delete unresolvable rows — rejected; pre-prod data has dev value.
- Force a placeholder `zatca_configs` row — rejected; misleading audit trail.
